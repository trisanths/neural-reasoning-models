# Retrieval training on real documents

Status: data built and audited, training and re-measurement in progress. Every
table below is generated by `src/realret/report.py` from record files it names,
and the record-file table at the top of that output carries each file's
modification time so a stale quote is visible rather than hidden.

## The failure this addresses

Every retrieval episode this model had ever trained on was invented here: our
systems, our 768-frame generated grammar, our task families, our page format.
It had never issued a query against text somebody else wrote and never seen a
question a person asked. The benchmarks it was then measured on were also
written here. On MMLU it scores 0.275 at n=200 against a 0.250 floor, an
interval that contains chance, while LFM2-350M at the same parameter count
scores 0.43 on the same harness.

## What was built

Three sources, all real, all with the passages the datasets ship.

| source | what a question is | what a document is | hops |
| --- | --- | --- | ---: |
| `hotpot_qa` | a HotpotQA distractor question | one of the ten titled Wikipedia paragraphs the dataset supplies, two of which support the answer | 2 |
| `natural_questions` | a Google query from MRQA's NaturalQuestionsShort | a passage of the Wikipedia page a human annotator marked | 1 |
| `trivia_qa` | a trivia question from MRQA's TriviaQA-web | a passage of a web document a search engine returned | 1 |

HotpotQA carries the largest share because chaining a retrieved result is this
project's one unfixed failure, and it is the only one of the three whose
retrieval corpus is multi-hop by construction: its eight distractors were
retrieved by the dataset's authors against the gold pair, so the bundle is a
retrieval corpus the dataset supplies rather than one assembled here.

MRQA supplies one passage document per question, so the bundle for those two
sources is that document's own passages plus mined negatives: passages
belonging to other questions that share an uncommon term with this one. A
negative about the same entity is the only kind worth having; a bundle of
unrelated pages makes any query look good.

## The trace

The episode format is the one `src/rl/env.py` and `src/evals/interactive.py`
already walk, and the prompt comes from `src/rl/env.py:build_prompt`, so the
world header is present. Without that header this checkpoint issues no
retrieval round, emits no answer marker, and runs to the token cap; the fault
has cost this project two results.

    <|world|> domain: web <|q|> question
    [ <|retrieve|> query <|result|> page ] x rounds
    <|a|> answer <|eot|>

The domain string is `web` for all three sources, one header rather than three,
so the model has to decide from the question whether an item needs chaining
instead of reading the answer off the header. The source is kept in the pack
index, which is what the per-source tables are grouped by.

Round one always writes the question itself as the query, trimmed to the
environment's 24 token cap by dropping stopwords first and then leading words,
always on a word boundary. This is the policy that has to transfer: a live web
search takes a question, not a term vector, and a model trained to open with
keyword soup carries the soup to the search box. Cutting on the raw token tail,
which is what the synthetic corpus renderer does, turns "Allie Goertz" into
"z"; that is fine for a synthetic question with a padding lead-in and wrong for
a real one.

Later rounds refine. A refinement starts from the question's content words and
adds bridge terms drawn only from the question and from pages already served,
chosen greedily by BM25 margin and accepted the moment the serving gate
actually returns the target with earlier rounds excluded. The no-clairvoyance
rule is the one `src/scrub/web_retrieval.py` enforces, and `src/realret/verify.py`
re-checks it from the written episode alone rather than from the object that
built it.

So a one-hop item whose question already surfaces its passage is one round. One
whose question misses is a miss and then a refinement. A HotpotQA item is the
question, the page it reaches, and then a query naming the bridge that page
introduced.

## What the mixture is

The synthetic corpus stays in. Half the examples are the diversity corpus the
previous run trained on, taken as a stride over its own shuffled pack so the
component proportions are preserved, and half are real. One to one by example
count; the token ratio is in the pack summaries because real traces are longer.

Keeping the synthetic half is not caution for its own sake: frame
generalisation reached 0.990 to 1.000 on held-out frames after corpus training
and the plan-length ceiling moved from three to forty-eight, and replacing
rather than mixing would put those at risk for a gain that is not yet measured.

## The budget

The project's standard, matched to `corpus-v1-8k` exactly: 8000 optimizer
steps, batch 32 run as micro-batch 8 with four accumulations, AdamW at 2e-5
with betas 0.9/0.95, no weight decay, gradient clip 1.0, 200 warmup steps,
cosine decay to a tenth, bfloat16 autocast, one L40S. The training pass is
`src/corpus/sft.py train` unchanged; only the pack it reads is new.

Matching the budget is the point. The ladder has been training well below
compute optimal, near 5.24 target tokens per parameter, and more steps would
probably help. Running more of them here would also mean the comparison against
`corpus-v1-8k` confounds the data change with a compute change, and the data
change is the question.
