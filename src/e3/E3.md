# A 350M model trained on regime_e3, and what its failures mean

Every architectural conclusion on this project so far rests on a checkpoint
that saw about 5.24 target tokens per parameter. That is a quarter of the
compute-optimal figure, so "the approach is wrong" and "the model never
learned to read" have been indistinguishable. This run separates them by
holding the architecture, the tokenizer and the objective fixed and moving
only the token budget.

Status: training is in flight. Numbers below that are marked in flight will be
replaced by measurements, not by estimates. Everything already measured names
its record file, and the figures whose record file is gone are marked
unverifiable where they appear rather than deleted. Every number this lane read
out of `/mnt/nvme/e3eval/` was on worker 2's instance store; the instance is
terminated and nothing under that path was mirrored to S3, so the MMLU n=1000
row and the n=500 eot-prefix control cannot be recomputed. The MMLU figures the
repository can still produce for this checkpoint are 0.2750 at n=200 and 0.2640
at n=500.

## What is being trained, and how it matches

The architecture is read off the checkpoint that produced 0.2750 rather than
off a config file. `bench_ours` prints the model config it loaded from
`runs/corpus-v1-8k/final.pt`:

    d_model 1024, n_layers 24, n_heads 16, d_ff 2816,
    vocab_size 32768, max_seq_len 4096, rope_theta 10000.0, norm_eps 1e-05

`configs/350m-e3-run.yaml` carries that block unchanged, and the trainer
reports 375,440,384 parameters, which is the number in the brief and in
`src/extern/LIQUID.md`. Tokenizer is `~/data/tokenizer_v2.json`, the same file.
Objective is next-token cross entropy through `src.train.cli`, the path every
ladder rung used.

Code identity was checked rather than assumed. Worker 3 runs an unpacked
tarball of commit 7932f04 and the dev box is a checkout at f252f4c, so the two
could have differed. They do not, on any file this experiment touches:

    src/train/{model,data,trainer,cli,tokenizer}.py
    src/extern/{bench,bench_ours}.py, src/evals/mc.py, src/rl/env.py
    configs/350m.yaml

all ten sha256 sums are equal across the two boxes.

### From scratch, not from the existing base

The run starts from random initialisation. Continuing from the corpus-v1-8k
checkpoint would confound the thing being measured: that checkpoint carries a
pretrain on a different corpus, an RL stage and a corpus SFT stage, so more
tokens on top of it would answer "does further training help this particular
model" rather than "what does this architecture do with enough data". From
scratch, the only variable that moves against the ladder rungs is the number
of tokens.

The cost of that choice is stated plainly: the new checkpoint has had no RL
and no SFT, so it is compared against a checkpoint that has had both. Where
the new model loses, that difference is a live alternative explanation and is
called out in the section where it applies.

### Deviations

Two, both forced, both small.

`train.compile` is true, where the ladder rungs left it false. It changes
throughput and not arithmetic: 5.42 seconds per optimizer step against 10.40
eager, measured on this box on the same config, which is a 1.92x speedup and
the difference between a reachable budget and an unreachable one. Loss at step
20 and step 40 agreed with the eager run to five decimal places
(9.034097 against 9.034083, 8.177904 against 8.177856), which is ordinary
non-determinism, not a different computation.

`schedule.warmup_phase_steps` is 0 where `configs/350m.yaml` has 55. That
setting front-loads a procgen stream supplied by `--warmup-bin`, and no such
file is passed here. regime_e3 already carries procgen inline at 5 percent of
its mix, so the warm up is in the data rather than in a separate phase.

## Two stages, and why the second one is required

corpus-v1-8k is not a pretrain. It is `rlsimple-503-921` (a pretrain on a
different corpus, then an RL stage) followed by 8,000 steps of SFT on the
diversity corpus. Reading that off `RETRAIN.md` changes the shape of this
experiment, because two of the four measurements are only defined on a model
that has had the SFT.

The frame and hop numbers are read off rollouts in the corpus trace grammar,
`<|world|> ... <|q|> ... <|retrieve|> ... <|result|> ... <|a|>`, over the
diversity corpus's own relation families. regime_e3 does not contain that
grammar; its worldgen component is a different generator. A from-scratch
regime_e3 model scored on those items would sit at its floor for a reason that
has nothing to do with the token budget, and reporting that as "frame
generalisation was lost" would be a measurement fault of exactly the kind this
project keeps finding.

So the run has two stages.

    Stage A   regime_e3 pretrain, 26,700 steps, 7.0B tokens, from scratch
    Stage B   Stage A + the corpus-v1-8k SFT recipe, unchanged

Stage B uses the identical pack the published run used, `mix1`, carried over
from the dev box and verified by sha256: 253,972 examples, 77,021,506 tokens,
the same per-component counts recorded in `RETRAIN.md`. The recipe is
`src.corpus.sft train` at its defaults, which are the published ones: 8,000
steps, batch 32 as micro-batch 8 with 4 accumulations, lr 2e-5, 200 warmup,
cosine to a tenth, weight decay 0.

That makes the comparison exact. Both sides end with the same SFT on the same
pack; they differ in what was underneath it.

    corpus-v1-8k   (old pretrain + RL) + mix1 SFT
    Stage B        (regime_e3 pretrain, 7.0B tokens) + mix1 SFT

Which measurement is read off which stage:

| measurement | stage | why |
| --- | --- | --- |
| MMLU 5-shot | A and B | closed book; A is the clean data-volume reading, B is matched to corpus-v1-8k |
| retrieval query rate | A and B | same |
| held-out frames | B | needs the corpus grammar |
| hop curve | B | needs the corpus relation families |

Stage A alone still answers the question the brief puts first. If a properly
pretrained 350M is at chance on MMLU before any SFT, no SFT stage is going to
be what was missing.

## The budget, audited

Measured on the box, not estimated:

| quantity | value |
| --- | --- |
| optimizer step | 5.42 s, from `loss.jsonl` elapsed deltas |
| tokens per optimizer step | 262,144 = 64 sequences x 4096 |
| throughput | 48,340 tokens/s |
| achieved | 158 TFLOPS against 181 TFLOPS dense bf16 peak on one L40S |
| micro batch | 4, the memory ceiling; 8 raises CUDA OOM at 4096 context |
| peak memory | 23.775 GB with compile, 34.287 GB without |

### The rate I first reported was measured on a quiet window

5.42 s/step is what the card does when nothing else is on it, and it is the
right number for a throughput claim. It is the wrong number for an ETA, because
the evaluation loop shares the card every 1000 steps and each cycle takes about
24 minutes.

Measured end to end across 2100 steps spanning two full evaluation cycles, the
run does 6.22 s/step, 42,137 tokens/s. Against the quietest 200-step window at
5.47 s/step that is 13.7 percent overhead, and it puts the whole run at 46.1
hours rather than 40.2.

This is worth naming rather than quietly correcting. Taking the fastest window
and reporting it as the rate is the same shape as taking the first N items of
an ordered file: a sample chosen where the number looks best. The end-to-end
figure is the one an ETA should be built on.

The overhead buys the curve, which is the deliverable, so it is accepted rather
than removed. The lever if it ever needs pulling is evaluating every 2000 steps
instead of every 1000, which halves the overhead and halves the resolution of
the curve. It is not pulled.

At that rate the whole 13,354,983,633-token corpus is one pass in 76.6 hours.
The budget actually set is 26,700 optimizer steps, which is the number already
written in `configs/350m.yaml` for this model size and described there as
"20 tokens per parameter at 262k tokens per optimizer step":

    26,700 steps x 262,144 tokens = 6,999,244,800 tokens
    6,999,244,800 / 375,440,384 params = 18.64 tokens per parameter
    40.2 hours

That is 3.56x the token budget behind the 0.2750 result and it lands on the
compute-optimal point the brief names. It is chosen over the full 13.36B for
one reason: the cosine schedule completes inside it, so the final checkpoint
is fully annealed rather than caught mid-decay at a high learning rate.

What is not covered, stated plainly: 6.36 billion tokens of regime_e3, a
little under half of it. The sampler draws uniform random 4097-token windows
across the entire 13.355B-token stream rather than reading it in order, so the
7.0B tokens seen are a random sample of the whole corpus and not its head.
With draws made with replacement, the expected share of distinct corpus tokens
touched is 1 - exp(-0.524), about 40.8 percent.

## Durability

Instance store is wiped on stop, so nothing lives only on the box.
`~/e3/s3_watch.py` pushes `loss.jsonl` every three minutes, a weights-only
copy of every 1000-step checkpoint to `runs/e3-350m/weights/`, and a full
optimizer-carrying checkpoint every 2000 steps to `runs/e3-350m/resume/`, then
prunes local checkpoints so /mnt/nvme cannot fill. A wiped instance store
costs at most 2000 steps of progress, about three hours, because that is the stride of the S3 copy that
carries optimizer state. The weights-only copy every 1000 steps is for
evaluation, not for resuming: restarting from it would restart Adam.

## What the 0.2750 actually was

The accuracy is not the interesting number. The prediction distribution is.

`corpus-v1-8k` answers A on roughly seven items in ten, at every sample size:

| n | predictions A / B / C / D | modal share | gold A share | always-A would score | model scored | artifact |
| ---: | --- | ---: | ---: | ---: | ---: | --- |
| 200 | 146 / 7 / 35 / 12 | 0.730 | 0.300 | 0.3000 | 0.2750 | `results/extern/bench/ours_corpus-v1-8k_mmlu.json`, recounted |
| 500 | 353 / 23 / 91 / 33 | 0.706 | 0.254 | 0.2540 | 0.2640 | `s3://decoupled-reasoner-009398924577/runs/real-v1-8k/results/mmlu_closed_corpus-v1-8k_n500.json`, recounted |
| 1000 | 695 / 48 / 188 / 69 | 0.695 | 0.220 | 0.2200 | 0.2450 | `/mnt/nvme/e3eval/mmlu_ref_n1000.json`, unverifiable |

The first two rows were recounted item by item off the `pred` and `gold` fields
of their record files and every cell reproduces. The n=1000 row is on the wiped
instance store and is kept marked rather than deleted.

A model choosing uniformly would sit near 0.25 on each letter. On the two rows
that can be checked this one puts 0.706 and 0.730 of its mass on the first
option, and its accuracy tracks how often A happens to be the gold answer in
the drawn sample: it scores 0.2750 where always answering A would score 0.3000,
and 0.2640 where always A would score 0.2540. On both samples it lands within
0.025 of the always-A baseline, on either side of it, against a 0.2500 floor.

So the old checkpoint is not guessing uniformly and it is not reading. It has a
positional prior on the first option and answers it almost regardless of the
question. "Indistinguishable from chance" understates the problem; the policy
is degenerate in a specific, measurable way.

This is the signature `src/extern/LIQUID.md` records for LFM2 without its bos
token, where predictions piled onto the first option 102 times in 200 and a
prepended bos token fixed it. Our tokenizer defines no bos token, so the
analogous control is the eot prefix, and it was run rather than assumed:

## The four measurements

In flight. Method is fixed and is recorded here before the numbers exist, so
the numbers cannot pick their own method.

MMLU goes through `src.extern.bench_ours` unchanged, the harness calibrated to
reproduce LFM2-350M at 0.4300 against a published 43.43. It runs at n=500 and
n=1000, seed 1234, 5-shot completion, on every 1000-step checkpoint, driven by
`src.e3.autoeval`, so the result is a curve against tokens seen rather than a
single end point.

Frame generalisation and the hop curve go through the corpus-v1-8k battery
with its flags unchanged, `src.corpus.evalrun gen` at temperature 0.0 and 1.0
for relations and `src.frames.cli eval` at 0.0 and 0.7 for frames, on the same
item files the published numbers were read from: `rel_heldout.jsonl` taken
from `runs/corpus-v1-8k/artifacts/relation/` and the 41-file frame eval set
from `~/sweep/eval/gen`, both verified by sha256 after transfer. `src.e3.hopcurve`
cuts the same rollout file by hop count and scores each cell with
`src/frames/score.py:summarize`, the scorer `rescore relation` itself calls.

Retrieval policy is measured on the closed-book pass of
`src.extern.retrieval_ours`, which needs no live web: with no serving surface,
`issued_query` is exactly whether the model emitted `<|retrieve|>`. The prompt
is built with the world header, `<|world|> domain: corporate <|q|> ...`, and
`max_new_tokens` is 256, not 64.

One number in the brief does not survive contact. The brief says the current
checkpoint issues roughly one query in twenty passes. On this pass, at n=200,
seed 1234, the old checkpoint issues one on 0.255 of items, not 0.05. The
0.05 presumably came from the live-web pass where a query can also fail after
being issued. Both checkpoints are reported here on the same closed-book pass
so the two sides of the comparison are the same measurement.

The budget question was put and answered: the run goes to step 26,700 and is

learning rate is a fact about the schedule, and it is reported that way rather
than patched. Every row of the curve carries an `anneal` column reading `mid`
until the last one, and the table says in words that earlier rows read low for
their token count.

immediately rather than absorbed, because a silent restart losing optimizer
state would change what the final number means. `~/e3/status.sh` counts
restarts out of `supervise.log` and a monitor raises them as alarms. The first
version of that counter produced a false alarm, because `grep -c` prints its
own zero and exits 1 when nothing matches, so a trailing `|| echo 0` appended a
second zero and the count stopped comparing equal to `0`. It now counts through
a helper that returns exactly one number.

## Modal share is the early signal

Accuracy is the number that matters at the end. Before the end, the prediction
distribution moves first: a model that begins to read will spread its answers
across the four options before it starts choosing the right one. The old
checkpoint sits at 0.695 to 0.730 on its most-chosen letter against 0.25 for
uniform guessing, so there is a lot of room for that to fall while accuracy is
still flat.

Modal share is computed at collate time from `pred_letter_counts`, which
`src.e3.autoeval` already records per checkpoint, so the running evaluation
loop did not have to be restarted to add it.

## Reading the Stage A rows without over-reading them

Stage A rows as they land, MMLU n=1000, floor 0.2500, all mid-anneal:

| checkpoint | tok/param | acc | 95% Wilson | A / B / C / D | modal share | issued query |
| --- | ---: | ---: | --- | --- | ---: | ---: |
| e3 step 1000 | 0.70 | 0.2440 | [0.2184, 0.2716] | 464 / 172 / 163 / 201 | 0.464 | 0.000 |
| e3 step 2000 | 1.40 | 0.2250 | [0.2002, 0.2519] | 589 / 129 / 213 / 69 | 0.589 | 0.070 |

The 5.24 carries an asterisk because it is the ladder rung figure quoted in the
brief, not something measured here; corpus-v1-8k's own pretrain budget sits
inside `rlsimple-503-921` and was not re-derived for this table. The e3 rows
are exact, being step count times 262,144 over 375,440,384.

The corpus-v1-8k row is the comparison's anchor and its record file is gone:
`/mnt/nvme/e3eval/mmlu_ref_n1000.json` was on worker 2's instance store and was
never mirrored. The row is kept because the e3 rows beside it were measured
against it, and it is marked because only the e3 side of that comparison can be
re-run. At the sample sizes this repository can still produce, the same
checkpoint reads 0.2750 at n=200 and 0.2640 at n=500, both with intervals
containing the floor, so the conclusion the anchor supports does not turn on
the missing file.

Accuracy is at chance on both rows and is expected to be: at 1.40 tokens per
parameter the model has seen a thirteenth of its budget and sits near peak
learning rate. The interval on step 2000 reaches 0.2519, so it still contains
the floor and the model is not below chance. No claim rests on either
accuracy.

The modal share is moving toward the old checkpoint's collapse, not away from
it: 0.464, 0.589, 0.600 against 0.695. The rise is decelerating, and what is
actually happening underneath is narrower than "collapse onto A". D is the
option being abandoned, 201 to 69 to 46, while B fell and then recovered, 172
to 129 to 182. Consecutive checkpoints agree on 0.696 then 0.824 of items, so
the predictions are also settling.

That is the caution from the first row coming true rather than a surprise. The
0.464 was consistent with an undertrained model having noisy logits, and it was
recorded as such rather than as a model starting to read. Two rows at 0.70 and
1.40 tokens per parameter are not a trend that has to hold to 18.64, and the
usual order is that a model first learns to answer with a letter, then
over-commits to the commonest one, then learns to discriminate. But the honest
statement today is that more tokens have made the answer policy more
degenerate, not less.

Retrieval is the one thing moving fast, and it is worth being careful about
what it means. Issued queries go 0.000, 0.070, 0.205 against the old
checkpoint's 0.255, and the rest of the generative behaviour has converged on
it too: naming no candidate on 0.945 against 0.950, strict accuracy 0.010 on
both. At 2.09 tokens per parameter, 11 percent of the budget, pretraining alone
has nearly reproduced a retrieval rate the old checkpoint bought with an
explicit SFT on retrieval traces.

That is a real difference in how the behaviour was acquired. It is not evidence
that the policy is good. The brief calls the old checkpoint's 0.255 a policy
failure rather than a comprehension one, so matching it is matching a failure.
Emitting `<|retrieve|>` more often could equally be the model copying a surface
pattern out of the webret traces rather than learning when a page would help.
`mean_rounds` is 0.000 on every row because the closed-book pass serves
nothing, so nothing here says whether a retrieved page would have been used.
Only the live-web pass answers that, and it is not run on intermediate
checkpoints.

The clean comparison on both axes is Stage B against corpus-v1-8k, because
both have then had the identical mix1 SFT and differ only in the pretrain
underneath. Stage A rows are the data-volume reading on closed-book accuracy
and a diagnostic on the other two, not a verdict.
